# ZashPOS decisions

| ID | Decision | Reason |
|---|---|---|
| D-001 | Base is the NexoPOS v6.3.0 fork (Laravel 12, Vue 3, Tailwind 4, Reverb) | Reuse a working POS and its module system |
| D-002 | Rebrand visible text only; never rename App\, Ns* classes, ns.* permissions or config keys | Keeps upstream merges and the module system working |
| D-003 | LICENSE (GPL-3.0) stays; footer says "Based on NexoPOS" | Licence compliance |
| D-004 | Revenue model is hosting, support and updates, not code secrecy | GPL: clients receive source. Confirm with a lawyer before selling |
| D-005 | First module is ZashDine (own design, no copied code or assets) | Restaurant vertical |
| D-006 | One instance per client, no multi-tenancy for now | Simplest to ship |
| D-007 | ZashMarket is a separate Laravel app, built after client #1 | Avoid premature work |
| D-008 | Tests only for risky logic; the rest is manual QA | Speed |
| D-009 | Cancel meal removes the product from unpaid dine-in orders via `OrderProduct::delete` + `OrdersService::refreshOrder` + stock return (same as order-update `__deleteUntrackedProducts`), not `deleteOrderProduct` | Core `OrderBeforeDeleteProductEvent` uses Bus `Dispatchable` and fatals; keep honest bill behaviour without a core edit |
| D-010 | `OrdersService::getOrder` eager-loads `customer.group` so reopened POS orders keep `minimal_credit_payment`; payment/layaway UI must error when group rules are missing instead of defaulting to 0 | Reopened carts previously crashed on `order.customer.group.minimal_credit_payment`; reselection was a workaround that could change the customer |
| D-011 | Treat `minimal_credit_payment` as a finite percentage `>= 0` (backend float/integer, `0` means no minimum). Accept only finite numbers or nonblank numeric strings; blank/NaN/nonnumeric values and booleans/arrays/objects are invalid and must fail closed | `Number('')===0`, `Number(false)===0`, `Number([])===0`, `Number(true)===1`, and `NaN >= 0 === false` previously coerced or skipped layaway validation |
| D-012 | Offer and persist only canonical IANA Zone identifiers; remap obsolescent links (e.g. `Canada/Pacific` → `America/Vancouver`) via `TimezoneCatalog` at runtime (no database rewrite of saved settings) | Backward Link names fail on some CI/system tzdata builds while preserving the same DST/offset rules as the Zone target |
| D-013 | Dine-in table pick, meal note and meal cancel use module-owned Vue popups through core `Popup.show` (Options API templates), not `window.prompt` / `window.confirm` | Touch-friendly POS/Floor UX with loading/error/retry, Escape/X dismissal, focus restore, and no double-submit; server occupancy checks stay authoritative |
| D-014 | Kitchen statuses are `pending → preparing → ready` or `pending/preparing → rejected`. Rejection keeps the order product and stock (bill unchanged); Floor cancel remains the charge-removal path. Cancel after `preparing`/`ready`/`rejected` requires `zash.dine.manage`. Unassigned categories keep `kitchen_id` null and appear in the Unassigned kitchen queue (never dropped). Phase 3a uses 5s polling; Phase 3b adds Reverb push while keeping polling as fallback | Separates kitchen refusal from waiter/manager cancellation; avoids silent meal loss |
| D-015 | Protect kitchen meals on order update via `OrderAfterCheckPerformedEvent` before product mutation; applicability is based on the persisted dine-in order and its kitchen rows (not the incoming type). Leaving dine-in with protected meals requires `zash.dine.manage`; after a permitted type change, kitchen rows are cancelled and the table is released so occupancy is not stranded. Guards resolve product identity the same way as `OrdersService::__buildOrderProducts` (`product_id` or `sku`, catalog→custom) and require `unit_quantity_id` to belong to that resolved product; quantity is checked too. Edit checks lock `order → order_item` and evaluate protection from those locked rows inside the persist transaction. Pending same-line product replacements re-resolve `kitchen_id` (Grill→Bar / Unassigned); started meals are never re-routed. Floor cancel and kitchen transitions lock `order → order_item` (then `order_product` for cancel) and re-check the locked row; kitchen CRUD uses `CrudService::$wrapSubmitInTransaction` so category sync failures roll back the kitchen row | Prevents waiter bypass via type change, SKU/`product_id` swap, or mismatched unit identifiers; keeps pending replacements correctly routed; avoids races with kitchen transitions and partial kitchen/pivot writes while keeping module hooks and a focused core opt-in |
| D-016 | Phase 3b realtime: Kitchen/Floor subscribe to private channels `zash-dine.kitchen` (chef/manage) and `zash-dine.floor` (waiter/manage). Board signals use `ZashDineBoardUpdated` (`ShouldBroadcast` + `ShouldDispatchAfterCommit`) with a thin payload (`event_id`, reason, ids); clients refresh via existing APIs so the database stays authoritative. Polling every 5s continues even when Echo/Reverb is connected or unavailable. Ready-meal alerts go to **`Order.author_id`** (the dine-in order owner / responsible waiter), not `OrderItem.author_id` (sync actor). Alerts create a `Notification` (source `zash-dine`, identifier `zash-dine-meal-ready-{itemId}`) and broadcast `ZashDineMealReady` on `App.User.{author_id}` for Floor snackbars — both only after the kitchen transaction commits (`DB::afterCommit`), and core `Notification*Event` broadcasts also implement `ShouldDispatchAfterCommit`. `App.User.{id}` auth requires the authenticated user to own that id. Kitchen/Floor wait for `window.Echo` (DOMContentLoaded + retry) and clear waiters on unmount; Floor stops listening for meal-ready without `Echo.leave(App.User.*)` so the dashboard notification subscriber stays intact. Reverb/broadcast failures after commit are logged and never fail the kitchen HTTP write | Avoids broadcasting rolled-back state; keeps role-scoped private channels; matches waiter ownership already stored on the order; prevents Echo init races and shared-channel teardown |
| D-017 | Modifier money is baked into `unit_price`: catalog `sale_price_edit` (wholesale: `wholesale_price_edit`) + Σ(`modifier.price` × modifier line quantity). `line_total = (unit_price − discount) × meal_qty` stays the core TaxService formula. Do not use `line_extra` for modifiers; the server ignores it. `ns-order-product-canonical-unit-price` adds the same surcharge before the core price-permission check so a valid modifier price is not a manual override. POS writes that baked `unit_price` before submit. Rows live in `zash_dine_order_product_modifiers` (name/price/ingredient snapshots, quantity, `stock_applied`). Required ingredient stock is modifier quantity × meal quantity; only the difference versus `stock_applied` moves (`sale-adjustment` / `return-adjustment` — never `sold`). Omitted metadata on existing lines reconciles persisted selections (surcharge, stock, fingerprint); explicit `[]` clears. Historical snapshots apply only to an unchanged selection on the same catalog product (fingerprint match); partial edits and product replacements re-validate membership and min/max against groups assigned to the incoming product. Void returns modifier stock idempotently and keeps history; delete after void does not double-return. Product-group assignment is centralized in `replaceProductGroups` (`zash.dine.manage`, validate-all-then-transaction). Hold keeps `stock_applied` at 0 until hold→non-hold. Protected meals compare a sorted `modifier_id:qty` fingerprint. | Meal quantity has to scale both the bill and ingredient stock. `line_extra` cannot do that. Snapshots and omit-reconcile keep sold terms honest; void/delete stay idempotent. |
| D-018 | Do not load `bootstrap/prefer-app-modules.php` from production `artisan` / `public/index.php`. Opt in with `ZASHPOS_PREFER_LOCAL_APP=1` (read at the top of `bootstrap/app.php`), `tests/bootstrap.php`, `scripts/local-artisan.ps1`, and e2e setup. Prefer a checkout-local `composer install` (real `vendor/`) when possible. | Shared-vendor junctions must not leak into shipped entry points; serve children still need App/Modules from this checkout. |
| D-019 | Ship ZashDine as a Modules-upload ZIP built by `PackageService` / `zash-dine:package` (stable entry order + fixed mtimes → reproducible SHA-256). Declare `<core min-version="6.3.0" />` and exclude `Tests/**` from the client ZIP. Validate install via upload (`zash-dine:validate-package-install`) on an instance with its own vendor/DB/env. UK VAT/receipt checks use GOV.UK/HMRC retailer invoice rules in docs; browser receipt HTML is automated, physical printers/tablets are explicitly hardware-gated. | Marketplace and client installs must match the Modules UI path; legal VAT display depends on store settings the operator configures. |
